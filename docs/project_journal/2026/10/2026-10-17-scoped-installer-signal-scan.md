# Scoped Installer Signal Scan

## Summary
- The ordinary current-v2 installation boundary keeps canonical verifier/controller workflows, managed CODEOWNERS coverage, the required ruleset, and the repository-wide default-workflow-permissions read-only preflight strict while treating unrelated workflow-local write permissions as operator-trust warnings.
- The installer uses a best-effort source-text keyword scan to block recognized explicit additional Codex gate callers and recognized uses of the reserved `codex/github-review-gate` signal. Recognized but unresolved candidates warn; unsupported syntax can be missed, even without a warning. Unrelated keywords and contexts do not block installation. The scan does not execute workflows, prove full data flow, prevent a malicious same-name forgery, or establish a unique producer.

## Current State
- The ordinary install does not require unrelated status, check, action, or contents publishers to be removed or isolated. Fragmented text, literal concatenations, and simple local-variable forms are scanned where possible. Discovered unresolved candidates receive warnings, but warnings do not exhaust unsupported forms. Unrecognized literal forms may pass the scan. Unrelated workflow-local write permissions remain operator-trust warnings. This policy does not relax the repository-wide default-workflow-permissions read-only preflight.
- `--reviewed-status-writer` remains an optional compatibility path for the older exact-digest and isolated-publisher check. It is not required for ordinary current-v2 installation; its stricter checks apply only when explicitly supplied.
- The historical organization handoff, bridge-removal, and source-only proof contracts remain frozen and strict. The prior `2026-10-16-reviewed-status-writers` note records its then-current decision and is not rewritten as though the policy had always been this way.
- HDR-streaming PR #363 restored `.github/workflows/transport-evidence-gate.yml` and `.github/workflows/transport-process-acceptance-gate.yml`; these unrelated transport status producers are left unchanged by ordinary gate installation.

## Decision and Reason
- Ordinary installation should not require refactoring unrelated transport, build, or release publishers. Joey accepted the shared GitHub Actions App and operator-trust boundary instead of an exhaustive unique-producer proof.
- Joey explicitly reaffirmed the accepted false-negative risk after another review requested seven additional syntax/transport recognizers. Do not add recognizers for those forms: curl's implicit POST, bare sequence markers, multiline flow collections, flow-step run values, folded run commands, gh stdin bodies and Octokit calls remain known warning-only coverage limits. Expanding each representation would move the preflight toward YAML, shell, HTTP-method and JavaScript interpretation without establishing a unique producer. The examples are technically real; their disposition is accepted risk under the ordinary-install contract, not a claim that they cannot publish a conflicting signal. See `docs/install/workflow-scan-risk-boundary.md` for the exact scope and review references. Future coverage can be proposed for a separate product need, not accumulated automatically from every new spelling. Canonical controls, runtime finding gates and strict historical/cleanup contracts are not waived.
- Apply the same false-negative decision to an individual block-sequence step written as a flow mapping (`- { uses: ... }`). In contrast, correct known-data false positives: context-like `env`/`with` values and YAML-looking selector text in a block scalar are not proof of a publisher or executable caller. Keep this a bounded scope correction, retain command/API publishing recognition inside run scalars, and resume actual selector recognition after dedent. An anchored context input is now covered as nonblocking data rather than a synthetic publisher fixture. Strict cleanup and execution-time review policy remain unchanged.
- Data classification applies to actual environment/input/output properties, not a job whose ID happens to be `env`, `with` or `outputs`; keep real gate selectors and job names visible in those jobs. CLI context flags also require a recognized publishing command/endpoint rather than matching arbitrary output such as `echo -f context=...`. Context and CheckRun-name extraction share an explicit GET/HEAD exclusion: non-POST is not synonymous with read-only, and PATCH name updates remain writers. Compare complete bounded folded job names, not their individual physical lines; incomplete or over-budget values warn rather than matching a prefix. These correct regressions introduced by scope/method filtering and existing false positives; they do not add syntax recognizers for the eight accepted coverage gaps.
- Bind `gh api` classification to its leading literal endpoint, including simple surrounding quotes, rather than searching payload text for an endpoint substring. A GraphQL query or unrelated REST request mentioning `/check-runs` or `/statuses/...` does not thereby publish the gate. Keep endpoint text raw enough for existing `/statuses/$SHA` forms; do not add a general argument/shell interpreter. Option-before-endpoint and other unsupported layouts can be missed under the existing best-effort risk boundary.
- Apply the data-versus-execution boundary to nested environment mappings and reusable-caller secret inputs as well, without hiding real jobs whose IDs have data-property spellings. Keep endpoint, method and CLI fields inside the same first-command prefix; parameters printed by a subsequent shell command do not belong to the API call. Reset local literal state at observed YAML step boundaries regardless of the first key, rather than carrying shell variables between isolated steps. These narrow false-positive corrections do not add publisher types, general shell interpretation or cross-step propagation analysis.
- Preserve block-scalar ownership: only run bodies participate in executable matching, while non-run scalar values and matrix expansion data are not publisher proof. A partial physical line, clipped input tail or shortened window value cannot establish exact equality or seed later literal composition; retain warning-only limits. Bind supported curl matches to the actual unambiguous URL operand, not header text. Restrict definite block-scalar job names to complete supported strip-chomp values rather than erasing meaningful spaces/newlines with trim. Unsupported curl options and scalar semantics remain warning-only coverage limits; do not add complete curl/YAML interpreters to eliminate those accepted unknowns.
- Keep request-host/body evidence conservative: a `gh api` field only proves the supported GitHub publication form on the default or explicit `github.com` host without `--input`. Other hosts, ambiguous hostnames and file/stdin bodies remain unclassified; do not read external body files. A supported curl publication requires HTTPS on `api.github.com`, no URL user-info, default/443 port and exactly one literal body option. Multiple bodies are deliberately not composed. This avoids blocking unrelated endpoints or treating query fields/body fragments as a proven publication, without adding a complete CLI/HTTP interpreter.
- Skip an entire known block-scalar run containing here-document-like `<<` text and clear local literals through that block. Emit a warning rather than interpret delimiters or classify generated configuration text as execution. This knowingly also skips lookalikes and real publishers in the same block, consistent with the accepted best-effort false-negative boundary.
- Omit all raw source diagnostic excerpts, retaining kind, workflow path, line and fixed explanatory messages. Authorization-only handling still missed quoted JSON credential fields; removing raw excerpts uniformly avoids accumulating secret-format regexes or exporting an unrecognized credential spelling. Operators use the source location to inspect the workflow themselves. Regression credentials use the approved synthetic catalog `joey-private-v3` records `bearer-a` and `api-key-a`; no real credentials are used.
- Treat repeated CLI method flags as unclassified instead of trusting the first occurrence or implementing the effective final method. Keep quoted semicolons inside a single statement rather than inventing an executable assignment from printed text. Both correct false-positive blocking while preserving the accepted incomplete shell/CLI interpretation boundary.
- Normalize local workflow paths at the ordinary scan comparison boundary so native Windows separators cannot make canonical workflows appear unrelated. Keep strict reviewed-writer matching and digest snapshots unchanged; this is a logical path-representation correction, not a new filesystem identity or race-hardening policy.
- Preserve exact YAML value identity and known field scope: quoted scalar prose cannot introduce more fields, and a job name's trailing comma/semicolon cannot be erased as though it were a shell/JavaScript terminator. Keep the existing bounded shell-expression handling separate. Likewise, supported literal curl publication reads a top-level string in a complete JSON object on its exact POST route; nested fields and update-route suffixes are not create evidence. CLI method flags are read from the existing tokenized argument positions rather than quoted header/body prose. These fix both false-positive blocking and a quoted-value false negative without adding new publisher types or exhaustive parsers.
- Keep encoded curl bodies such as `--data-urlencode` unclassified. Its raw argument is not the emitted JSON; a local curl help check confirmed that transport encodes POST data. Do not simulate encoding to preserve a blocking match. This removes an earlier false-positive fixture expectation and follows the same unsupported-body boundary.
- Apply the already-approved false-negative boundary to descriptor-redirection transport (`2>&1` / `&>`): the prefix scan can stop early and miss a real gh/curl publisher, but adding shell-redirection grammar is outside this installer slice. Record the technically valid review example as an accepted warning-only gap, with a source comment and regression, rather than accumulating another shell recognizer. Remove the new `JSON.parse` quoted-string exception as well; programmatic JSON parsing stays unclassified, so display text cannot become executable fields. The original eight warning-only examples, strict installer modes and runtime findings gate remain unchanged.
- Parse CLI payload fields only at their supported tokenized option positions; flag-shaped header prose is data. Bind the existing supported CheckRun name field to POST collection/PATCH update routes and status context to its supported route/method. Unsupported endpoints or parameter forms remain unclassified rather than growing a full request interpreter.
- Keep that CLI grammar closed: consume known option values, leave unknown layouts and dollar-containing field values unclassified, and compare literal API field keys case-sensitively. Tokenization loses the distinction between a quoted literal dollar expression and a shell expansion; do not infer one from the other. This consciously preserves warning-only coverage loss instead of adding shell expansion semantics. Missing field arguments must not throw.
- Support the ordinary `-F` alias for the already-supported `--field` option; local `gh api --help` confirms the shared typed-parameter role. This is a small literal alias, not typed-value/file evaluation. In contrast, decoding quoted YAML run scalars or escaped YAML job names would add another syntax interpreter; keep those technically valid publisher/collision examples as documented warning-only gaps with source comments and regressions, consistent with the accepted false-negative boundary. The original eight examples and strict/runtime controls remain unchanged.
- Exclude known literal foreign-repository CLI/curl destinations only when the ordinary installer has a valid target identity; a writer in another repository cannot publish this repository's required check. Reuse the remote installer's existing identity and optionally read local origin once for offline preparation, without an API call or a new origin requirement. Missing, invalid or unreadable origin emits a fixed generic warning and retains conservative scanning. Compare GitHub repository names case-insensitively, do not infer dynamic/encoded destinations as foreign, and preserve strict historical/proof paths. This corrects false-positive scope rather than broadening syntax coverage.
- Preserve known data and exact YAML scalar identity in two additional representations: inline flow `env`/`with`/`outputs`/`secrets`/matrix mappings do not publish a nested context by themselves, and `//` is not a YAML comment that can be removed from a job name. Fix those false-positive classifications without introducing general YAML parsing or executable-language comment semantics. Existing real publisher/job controls and accepted coverage gaps remain in force.
- Apply the same known-data boundary to actual strategy, container, services and default-run-settings properties. Their nested matrix/environment configuration does not publish a status simply because a context-like key appears in a one-line flow container. Use the existing property/indentation classifier for block and supported flow forms; do not restore recursive field-text reconciliation or add a parser. Preserve jobs whose IDs use those names and subsequent real run publishers. This addresses the next reported false-positive representation, not a new producer guarantee.
- Strip an existing supported simple anchor prefix before the empty/flow data-mapping test, without resolving aliases or YAML data flow. Do not turn a trailing backslash inside an open single-quoted curl argument into shell continuation evidence; leave that payload unclassified instead of reconstructing valid JSON from different bytes. Both correct false-positive identity without adding a shell/YAML interpreter.
- Use fixed ordinary permission-warning text, omitting parser exception details and parsed permission labels. Both can contain raw workflow source; the permissive permission collector can return arbitrary label spellings as well as throw on opaque values. Preserve workflow path/kind/line and operator-trust guidance, and use the approved `joey-private-v3` `api-key-a` fixture to assert opaque scalar/child values do not leak. Strict validation behavior is unchanged.
- Apply the existing folded-run warning-only boundary to the whole known `>` run block: physical lines are not separate shell commands after YAML folding. Do not reconstruct folded strings. For host overrides, a bounded-source `GH_HOST` mention makes implicit-host gh publication unclassified across that scan; intentionally accept loss for inactive/data/comment references instead of implementing scoped environment inheritance. Explicit supported github.com hostname arguments remain eligible. These are conservative scope guards under the accepted false-negative contract, not a new environment interpreter.
- Do not erase nonspecial double-quoted shell backslashes into a different name or accept a quoted endpoint prefix before a concatenated suffix. Unsupported words/concatenations stay unclassified. Likewise leave literal curl Host header overrides unclassified instead of inferring virtual-host routing from only the URL. Preserve ordinary supported literal publisher controls without claiming complete shell/HTTP semantics.
- Physical lines in an incomplete literal-run shell command or a multiline quoted YAML scalar cannot independently prove executable commands or mapping properties. Keep unsupported continuation regions unclassified rather than reconstructing their runtime value. At known indentless step-sequence boundaries, classify the step before job-property names so a display name cannot become a reserved job CheckRun. These correct source-role false positives without expanding the completeness contract.
- Treat a recognized matrix-key mention in a known job as uncertainty for exact emitted job-name identity, without expanding combinations or proving whether GitHub decorates every name. Likewise, a recognized explicit YAML shell configuration makes command-publisher recognition uncertain across that source instead of interpreting custom shells or default inheritance. These deliberately broad guards accept missed real publishers/names, including inactive/data configuration references; actual action callers and unaffected job-name controls remain separately eligible. Suppressed publisher candidates do not consume the matching-result budget. This follows the accepted false-negative boundary rather than introducing matrix or shell interpreters. The accepted matrix examples are block-form `env:` and reusable `with:` mappings with nested `matrix:` keys ([review finding #4306626036](https://github.com/Joey-Tools/codex-review-gate/pull/128#discussion_r4306626036)); that finding's inline-map example is not reproduced by this heuristic. The accepted shell examples include a job ID named `shell` or an `env`/`with` entry named `shell` ([review finding #4306626032](https://github.com/Joey-Tools/codex-review-gate/pull/128#discussion_r4306626032)). No YAML role or `strategy.matrix` parser is added; action-caller and unaffected job-name recognition remain eligible, and strict canonical/runtime controls remain unchanged.
- Correct the genuine false positives in [review finding #4306626037](https://github.com/Joey-Tools/codex-review-gate/pull/128#discussion_r4306626037), [#4306626046](https://github.com/Joey-Tools/codex-review-gate/pull/128#discussion_r4306626046), and [#4306626049](https://github.com/Joey-Tools/codex-review-gate/pull/128#discussion_r4306626049) by preserving YAML scalar identity instead of applying shell/JavaScript substitution, comparing curl request methods without case normalization, and retaining `=` in attached curl short-option values. [Review finding #4306626040](https://github.com/Joey-Tools/codex-review-gate/pull/128#discussion_r4306626040) is addressed by rendering workflow paths in control-safe form before diagnostics. These are narrow value-identity and diagnostic-boundary corrections; they do not add general YAML, shell, or request interpreters.
- The reported remote bootstrap `undefined` policy failure did not reproduce: `validateCanonicalV2WorkflowInventory` already uses the JavaScript destructuring default `strictUnrelatedWorkflows = legacyBridge`, which applies both to an omitted property and an explicit `undefined`. Retain that implementation and test ordinary versus legacy-bridge defaults inside the existing bootstrap registration; do not add a production default solely to satisfy the incorrect premise. Explicit strict cleanup/proof callers remain unchanged.
- A context-like local variable assignment only stores a value; it cannot publish a status on its own. Keep that literal available for later recognized publisher matching, but remove standalone assignment blocking proof. Similarly, a reusable workflow in the same source repository is not necessarily the gate: restrict legacy caller identity to `Joey-Tools/codex-review-gate/.github/workflows/codex-review-gate.yml`, preserving the actual legacy caller while leaving unrelated callable workflows nonblocking. These narrow existing false positives without adding new producer syntax.
- Scan common literal fragments within bounded local segments, without executing scripts or resolving full data flow. Keep potential unresolved collisions as warnings, and never let the warning-output cap suppress a definite signal match.
- PR review exposed a missed simple YAML anchor prefix and an overbroad exact-token fallback. Recognize anchored literal callers and actual job-name fields, including simple quoted keys, observed indentation, and bounded folded values. Keep plain references in output, queries, root/step names, and artifact labels nonblocking; retain definite context/check-name publishing fields and explicit CheckRun API payload matches. This remains a heuristic, not full YAML interpretation or general alias/data-flow resolution.
- A later review identified three more explicit forms: a caller referenced through a previously declared scalar alias, an anchor prefix on a reserved job/context value, and a direct JSON CheckRun publication payload. Cover these bounded literal forms consistently rather than adding a general YAML or command interpreter. Unresolved or complex aliases remain warnings, and ordinary text or read-only references remain nonblocking; the scanner still does not prove a unique publisher.
- Scalar-alias handling is limited to previously declared simple literals in the current document, with at most 32 names and 512 characters per value; document boundaries reset that state. Literal JSON publication matching requires one explicit curl POST with a matching `/check-runs` name or `/statuses/<sha>` context payload. Explicit backslash continuations are joined under a bounded local-command budget, not across job, step, or document boundaries. It does not associate independent commands or resolve arbitrary payload variables/files. These limits preserve the approved best-effort boundary instead of claiming exhaustive alias or shell interpretation.
- Role evidence matters for both directions of the heuristic: recognize simple quoted job IDs in flow mappings, but do not classify a `with.uses` input as an executable selector. Only clear job/step selectors block as callers; uncertain positions warn rather than upgrading data references into collision proof.
- Handle direct flow-map properties independently of their order or unrelated nested permission values. A quote-aware local map/list reader is capped at 2048 characters and depth 8; incomplete or over-budget structures warn. Inspect only direct job `name`/`uses` and step `uses`, skipping nested input data. This fixes common literal forms without claiming general YAML interpretation. Literal curl status-context publication and the documented `gh api --raw-field` spelling receive the same bounded treatment as their existing CheckRun and short-flag forms.
- Keep policy selection explicit at post-cleanup closures. Bridge-free consumer derive/verify must not inherit the ordinary warning-only default; every repeated closure read uses strict inventory validation. Existing apply/source-proof paths already require the bridge profile, and the shared explicit policy fixes that invariant for them too. Preserve existing digest/content/isolation-validated reviewed-writer exceptions where the full consumer cleanup profile admits them; source/organization proof restrictions remain unchanged. The ordinary staging/activation default is intentionally warning-only and must not leak into evidence used to remove or verify removal of legacy protections.
- Align the root Chinese README and packaged READMEs/security guidance with the ordinary operator-trust boundary. The existing release manifest describes its historical exact source commit; documentation corrections do not rewrite that released payload, change executable runtime behavior, or authorize a release or alias move.
- Restore the HDR transport files to their installation base; the removed isolation requirement must not leave incidental runner, publishing, or lint-policy changes behind.
